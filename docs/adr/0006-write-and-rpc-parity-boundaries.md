# Write and RPC: full match core, partial return body and GET RPC

Clients must write **resources** and call **RPC** with a truthful PostgREST-shaped contract on MySQL 8. **Decision** (from [Decide write and RPC parity boundaries](https://github.com/jonbaldie/myrest/issues/10)): ordinary `POST` / `PATCH` / `DELETE` (including bulk `POST`), primary-key upsert, write safety filters, listed write preferences (`missing=default`, `max-affected`, preference handling), and writes on writable views are **full match**. `Prefer: return=minimal` and `headers-only` are **full match**; `return=representation` is **partial match** (honest body only when myrest can return affected rows). **Embed** after write is **full match** only with a representation body and a **relationship** in the **schema cache**. **RPC**: `POST` and named arguments are **full match** for functions; procedures use the same `/rpc` path as a myrest extension with one stable response shape. `GET` **RPC** is **partial match** (read-safe routines only; see [GET /rpc read-safe routines](../rpc-get.md)). Row-set **RPC** results support read-style filter/order/page/**embed** as **full match**; those features on scalar results are **not supported**. Labels live in the Write and RPC **capability areas**.

**Why:** Keep the main write and call paths honest for existing clients; name the return-body and read-safe **RPC** limits instead of silent drift; treat procedures as the same URL family rather than a second API.
